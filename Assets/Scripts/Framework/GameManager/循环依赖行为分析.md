# 循环依赖行为分析与测试

## 🔍 循环依赖会发生什么？

### 当前实现的行为

在当前的依赖注入实现中，**循环依赖不会导致死循环或栈溢出**，但会导致**单向注入失败**。

### 原因分析

当前的初始化流程分为三个独立阶段：

```
阶段1: 创建所有Manager实例
  ├─ ManagerA 创建 ✅
  └─ ManagerB 创建 ✅

阶段2: 依赖注入（按创建顺序）
  ├─ 为 ManagerA 注入依赖
  │   └─ 尝试注入 ManagerB → ✅ 成功（ManagerB已创建）
  │
  └─ 为 ManagerB 注入依赖
      └─ 尝试注入 ManagerA → ✅ 成功（ManagerA已创建）

阶段3: OnCreate生命周期
  ├─ ManagerA.OnCreate() ✅
  └─ ManagerB.OnCreate() ✅
```

**结论**：在同一层级（都是Data/Message/Logic）的循环依赖，**两个Manager都能成功注入对方**！

## 📊 测试场景

### 场景1：同层级循环依赖（都是DataBehaviour）

```csharp
// ManagerA
[Inject]
private ManagerB _managerB;

// ManagerB
[Inject]
private ManagerA _managerA;
```

**预期结果**：
- ✅ 如果 A 和 B 在同一初始化批次，**双方都能成功注入**
- ⚠️ 但这种设计通常表明架构有问题

### 场景2：跨层级"循环"依赖

```csharp
// LogicManager
[Inject]
private DataManager _dataManager;

// DataManager
[Inject]
private LogicManager _logicManager; // ❌ 不应该这样做！
```

**实际结果**：
- ✅ LogicManager 能成功注入 DataManager（Data先初始化）
- ❌ DataManager 注入 LogicManager 失败（Logic还未创建）
- ❌ 错误日志：[依赖注入失败] 类型: DataManager, 字段: _logicManager...

## ⚠️ 循环依赖的问题

即使技术上可以实现循环依赖，也**强烈不推荐**使用，原因：

### 1. 设计问题
循环依赖通常表明：
- 职责划分不清晰
- 耦合度过高
- 架构设计有缺陷

### 2. 维护困难
- 难以理解代码逻辑
- 修改一个影响另一个
- 测试和调试困难

### 3. 潜在风险
- OnCreate中相互调用可能导致未初始化状态
- 逻辑执行顺序不确定
- 未来重构困难

## 💡 如何避免循环依赖

### 方案1：提取公共依赖
```csharp
// 不好的设计
ManagerA ←→ ManagerB

// 改进的设计
ManagerA → SharedDataManager ← ManagerB
```

### 方案2：引入中介者
```csharp
// 不好的设计
UIManager ←→ GameLogicManager

// 改进的设计
UIManager → EventManager ← GameLogicManager
```

### 方案3：单向依赖
```csharp
// 不好的设计
LogicManager ←→ DataManager

// 改进的设计
LogicManager → DataManager
(Data不依赖Logic)
```

### 方案4：使用事件系统
```csharp
// 不好的设计
ManagerA [Inject] ManagerB
ManagerB [Inject] ManagerA

// 改进的设计
ManagerA 发布事件 → EventBus → ManagerB 订阅事件
ManagerB 发布事件 → EventBus → ManagerA 订阅事件
```

## 🔧 检测循环依赖（未来改进）

可以在依赖注入时添加循环依赖检测：

```csharp
private static HashSet<Type> _injectingTypes = new HashSet<Type>();

private static void InjectDependencies(object target)
{
    Type targetType = target.GetType();
    
    // 检测循环依赖
    if (_injectingTypes.Contains(targetType))
    {
        Debug.LogWarning($"⚠️ 检测到循环依赖: {targetType.Name}");
        return;
    }
    
    _injectingTypes.Add(targetType);
    
    // ... 注入逻辑 ...
    
    _injectingTypes.Remove(targetType);
}
```

但在当前的三阶段初始化中，这个检测意义不大，因为不会发生真正的循环。

## 🎯 最佳实践

1. **遵循单向依赖原则**
   - Logic → Message/Data
   - Message → Data
   - Data → Data (谨慎使用)

2. **发现循环依赖时重构**
   - 提取公共服务
   - 使用事件系统解耦
   - 重新思考职责划分

3. **定期review依赖关系**
   - 使用依赖关系图可视化
   - 及时重构不合理的依赖

## 📝 总结

| 情况 | 技术上是否可行 | 是否推荐 | 说明 |
|------|--------------|---------|------|
| 同层级循环依赖 | ✅ 可行 | ❌ 不推荐 | 双方都能注入，但设计有问题 |
| 跨层级"循环"依赖 | ⚠️ 部分可行 | ❌ 绝对禁止 | 违反架构原则 |
| 单向依赖 | ✅ 可行 | ✅ 推荐 | 清晰、易维护 |

**记住**：能做到 ≠ 应该做！循环依赖虽然技术上可行，但应该被视为代码异味（Code Smell），需要重构。
